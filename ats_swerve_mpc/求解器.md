这份文档描述的对象不是一个孤立的 MPC 求解器，而是 ATS 四驱四转舵轮导航链中的完整“规控设计”。JPS 负责离散全局拓扑搜索，MINCO S3 和独立 yaw 负责把拓扑路线变成连续、时间化、可检查的轨迹，footprint safety 与 Local Collision Repair 负责候选轨迹安全，Goal Manager 负责目标身份和执行授权，`ats_swerve_mpc` 负责在授权 reference 上做 SE(2) 跟踪并输出车体系速度。MPC 只是执行跟踪层，不能替代地图融合、全局搜索、MINCO 平滑、目标授权或故障恢复。

完整主链为：

```text
Point-LIO / registered_scan
    -> ROGMap probability, inflation, 3D ESDF
    -> numerical ground projection
    -> ats_rog_map_adapter terrain/static/slope fusion
    -> immutable PlanningMapSnapshot
    -> Goal Manager goal/action, lease and identity checks
    -> JPS (GridJps, optional controlled A* fallback)
    -> MINCO S3 position trajectory + independent yaw spline
    -> clearance, oriented footprint safety, Local Collision Repair
    -> final retimed ExecutionCommand
    -> TrajectoryTracker
    -> SE(2) iLQR MPC (QP shadow is diagnostic only)
    -> four-swerve feasibility checks
    -> /cmd_vel_mpc -> twist_to_motion_ctrl -> /motion_control
    -> MuJoCo or real chassis
```

本文保留后续的 MPC 数学、代价和约束细节，并补充各层之间的 frame、time、generation、QoS、ownership、fail-closed 和实车准入契约。凡是“已验证”只指文末列出的实际源码、单测和运行证据；未在目标机测量的实时性、内存和物理接触不作为实车性能结论。

结论：当前 `ats_swerve_mpc` 是一个“有限时域、非线性 SE(2) 轨迹跟踪 MPC”，内部采用手写的 iLQR/Gauss-Newton 迭代求解。它不是 OSQP、IPOPT、CasADi 或标准 QP/NLP 求解器，也没有把四个舵角作为独立状态进行动力学优化。

**3. SE(2) 离散动力学**

动力学函数位于 [`se2_mpc_controller.cpp:40`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/se2_mpc_controller.cpp:40)。

使用显式 Euler 离散化：

$$
x_{k+1}
=
x_k+
\Delta t
\left(
v_x\cos\psi_k-v_y\sin\psi_k
\right)
$$

$$
y_{k+1}
=
y_k+
\Delta t
\left(
v_x\sin\psi_k+v_y\cos\psi_k
\right)
$$

$$
\psi_{k+1}
=
\operatorname{wrapToPi}
\left(
\psi_k+\Delta t\,\omega_z
\right)
$$

其中：

- `dt` 是预测步长；
- 当前配置为 `0.05 s`；
- `horizon=30`；
- 预测时域约为 `1.5 s`。

角度通过：

```cpp
atan2(sin(angle), cos(angle))
```

归一化到 `(-pi, pi]`，避免跨 `pi` 时出现角度跳变。

对应雅可比在 [`se2_mpc_controller.cpp:54`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/se2_mpc_controller.cpp:54) 中计算：

```text
A = df/dx
B = df/du
```

iLQR 的 backward pass 使用这两个矩阵对当前轨迹进行局部线性化。

**5. MPC reference horizon 构建**

`buildHorizon()` 位于 [`trajectory_tracker.cpp:189`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/trajectory_tracker.cpp:189)。

每一个控制周期，轨迹跟踪器会生成：

```text
horizon + 1 = 31 个参考状态
```

每个参考点包含：

```text
reference.state   = [x, y, yaw]
reference.control = [vx, vy, wz]
```

轨迹位置速度先通过相邻世界系点计算：

$$
v_{world}
=
\frac{p_{k+1}-p_k}{t_{k+1}-t_k}
$$

再根据参考 yaw 转换到车体系：

$$
v_{body}=R(\psi)^T v_{world}
$$

代码对应 [`trajectory_tracker.cpp:231`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/trajectory_tracker.cpp:231)。

因此，当机器人 yaw 为 90 度、世界系速度沿 y 轴时，MPC 会得到正确的车体系前向或横向速度，而不是错误地把世界速度直接当成车体速度。

**6. 代价函数**

代价函数位于 [`se2_mpc_controller.cpp:252`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/se2_mpc_controller.cpp:252)。

每个阶段的代价为：

$$
J_k=
e_{x,k}^TQe_{x,k}
+
e_{u,k}^TRe_{u,k}
+
\Delta u_k^TR_d\Delta u_k
$$

其中：

$$
e_{x,k}=x_k-x_k^{ref}
$$

yaw 误差会单独进行 `wrapToPi` 处理。

$$
e_{u,k}=u_k-u_k^{ref}
$$

$$
\Delta u_k=u_k-u_{k-1}
$$

最终总代价为：

$$
J=
\sum_{k=0}^{N-1}J_k
+
e_{x,N}^TQ_Te_{x,N}
$$

当前配置为：

```yaml
state_weight:        [18.0, 18.0, 4.0]
terminal_weight:     [28.0, 28.0, 8.0]
control_weight:      [0.12, 0.12, 0.08]
control_delta_weight: [0.7, 0.7, 0.25]
```

含义是：

- x/y 位置误差权重较高；
- yaw 误差权重相对较低；
- 控制量变化被惩罚，降低舵轮速度和车体速度突变；
- 终端误差权重更高，推动预测末端靠近参考轨迹。

**7. Warm Start**

warm start 逻辑位于 [`se2_mpc_controller.cpp:282`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/se2_mpc_controller.cpp:282)。

第一次求解：

```text
初始控制序列 = reference.control
```

后续周期：

1. 将上一周期控制序列左移一格；
2. 当前 reference control 与上一周期 warm control 混合：

```text
0.7 * warm_control + 0.3 * reference_control
```

3. 对每个控制步重新执行约束裁剪；
4. 求解完成后保存新的控制序列；
5. 只发布第一个控制量；
6. 下一个周期重新预测和优化。

急停、定位异常、轨迹失效、求解失败时调用 `reset()`，清空 warm start，避免旧控制序列重新驱动车辆。

**8. iLQR backward pass**

反向递推位于 [`se2_mpc_controller.cpp:314`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/se2_mpc_controller.cpp:314)。

终端初始化：

$$
V_x=2Q_Te_N
$$

$$
V_{xx}=2Q_T
$$

然后从 $N-1$ 反向递推到 0，计算局部二次模型：

```text
Q_x
Q_u
Q_xx
Q_ux
Q_uu
```

`Q_uu` 会加入正则化：

$$
Q_{uu}
\leftarrow
Q_{uu}+\lambda I
$$

当前：

```yaml
regularization: 1.0e-5
```

使用 Eigen `LDLT` 分解求解前馈和反馈增益：

$$
k_k=-Q_{uu}^{-1}Q_u
$$

$$
K_k=-Q_{uu}^{-1}Q_{ux}
$$

如果：

- `LDLT` 分解失败；
- 增益包含 `NaN/Inf`；
- 参考长度不足；

则本周期求解失败，不会把旧 warm start 冒充成新的闭环解。

**9. Forward pass 和线搜索**

主求解器位于 [`se2_mpc_controller.cpp:378`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/se2_mpc_controller.cpp:378)。

候选控制为：

$$
u_k^{candidate}
=
u_k+
\alpha k_k+
K_k(x_k^{candidate}-x_k)
$$

其中：

```yaml
max_iterations: 6
line_search_decay: 0.5
min_line_search_step: 0.05
convergence_tolerance: 1.0e-3
```

线搜索过程：

```text
alpha = 1.0
如果代价没有下降，则 alpha *= 0.5
直到 alpha < 0.05
```

只有满足：

```text
candidate_cost + 1e-9 < current_cost
```

才接受候选控制。

这里有一个重要语义：

- 反向递推成功，说明本周期至少获得了数值可信的反馈增益；
- 线搜索没有接受候选，不一定代表失败；
- 如果当前 warm start 已经是约束可行驻点，候选可能被约束裁剪回原序列；
- 只有 backward pass 奇异、代价非有限或序列长度错误，才判定求解失败。

**10. 四舵轮约束实现**

四个轮心位置由：

```text
(+wheel_base_x, +wheel_base_y)
(+wheel_base_x, -wheel_base_y)
(-wheel_base_x, +wheel_base_y)
(-wheel_base_x, -wheel_base_y)
```

定义。

每个轮子的车体系速度为：

$$
v_{i,x}=v_x-\omega_z y_i
$$

$$
v_{i,y}=v_y+\omega_z x_i
$$

实现位于 [`se2_mpc_controller.cpp:130`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/se2_mpc_controller.cpp:130)。

约束分三层：

1. 车体速度限幅：

$$
|v_x|\le v_{x,max},\quad
|v_y|\le v_{y,max},\quad
|\omega_z|\le \omega_{z,max}
$$

2. 单轮速度限幅：

$$
\max_i\|v_i\|\le v_{wheel,max}
$$

如果超过上限，代码对整个 `[vx, vy, wz]` 做等比例缩放，保持同一个车体 Twist，不单独修改某个轮子。

3. 车体加速度限幅：

$$
|\Delta v_x|\le a_{x,max}\Delta t
$$

$$
|\Delta v_y|\le a_{y,max}\Delta t
$$

$$
|\Delta\omega_z|\le a_{\omega z,max}\Delta t
$$

舵轮模块增量约束位于 [`se2_mpc_controller.cpp:159`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/se2_mpc_controller.cpp:159)。

单轮速度变化不能超过：

$$
\|v_i^k-v_i^{k-1}\|
\le
a_{wheel,max}\Delta t
$$

舵角变化通过两个连续轮速向量的真实夹角计算：

$$
\Delta\theta_i=
\arccos
\left(
\frac{v_i^k\cdot v_i^{k-1}}
{\|v_i^k\|\|v_i^{k-1}\|}
\right)
$$

代码没有对点积取绝对值，因此 180 度反向会被正确识别为舵角大变化。

如果候选控制不可行，则在：

```text
previous -> limited
```

的线段上执行 40 次二分搜索，找到最大可行比例。实现位于 [`se2_mpc_controller.cpp:203`](/home/kong/ATS_2026_snetry_test/src/ats_sentry_nav/ats_swerve_mpc/src/se2_mpc_controller.cpp:203)。

这是一种“候选控制投影/回退”策略，不是将约束直接纳入完整的 constrained iLQR 或 QP。

## 15. 这不是“只调 MPC”的规控系统

### 15.1 层次职责

ATS 的规划和控制必须按行为所有者分层。每层只消费自己需要的契约，不把下游方便的数据格式反向当成上游权威：

| 层 | 输入 | 输出 | 不负责的事情 |
| --- | --- | --- | --- |
| Point-LIO | LiDAR、IMU、外部观测 | `/localization`、`/registered_scan` | 不生成规划地图，不替代 ROGMap |
| ROGMap | 注册点云、位姿、概率参数 | occupancy、inflation、3D ESDF、ground projection service | 不发布规划执行命令，不做 JPS |
| ROGMap adapter | ROGMap 数值投影、静态墙、terrain、slope | `PlanningMapSnapshot`、ready/status heartbeat | 不从可视化点云反解析 ESDF |
| Goal Manager | goal、localization、snapshot/status | goal identity、lease、`ExecutionCommand` | 不把普通 Path 直接授权为运动 |
| JPS | immutable occupancy/signed-distance snapshot | 离散拓扑路径 | 不做时间分配、yaw、速度和舵角优化 |
| MINCO S3 | JPS waypoints、时间和边界条件 | 连续 position trajectory | 不绕过 footprint gate 或执行授权 |
| 独立 yaw | position route、yaw policy、gimbal state | yaw spline/authority | 不改变 JPS 的障碍拓扑 |
| Footprint/repair | candidate trajectory、oriented footprint、snapshot | 安全 candidate 或拒绝 | 不替代底盘动力学约束 |
| ExecutionCommand | 已审计 candidate、goal identity | 最终 retimed executable reference | 不接受迟到旧规划 |
| SE(2) MPC | 当前状态、已授权 reference | `/cmd_vel_mpc` body Twist | 不搜索全局路线、不融合地图 |
| chassis adapter | `/cmd_vel_mpc` | `/motion_control` | 不产生第二个速度 owner |

因此，“MINCO 不平滑”“一个点过不去就卡住”“RViz 路径颜色混淆”和“QP 是否可行”不能只在 MPC 求解器内部解决。它们分别属于轨迹生成/修复、Goal Manager 进展看门狗、可视化 topic ownership 和执行层求解器准入问题。

### 15.2 不可替代的约束

以下约束是设计边界，不因为换用 QP 或更换规划器而消失：

1. Point-LIO 继续提供定位和 registered scan；ROGMap 不是定位器。
2. 四舵轮控制量是车体系 `[vx, vy, wz]`，状态是世界系 `[x, y, yaw]`；不得加入 `vy=0`、差速或 ICR 假设。
3. JPS、MINCO S3、独立 yaw、footprint gate、Local Collision Repair 和 `ats_swerve_mpc` 必须保留。
4. unknown、outside-map、occupied、stale、lease 失效和 unsafe trajectory 默认 fail-closed，输出确定性零速度。
5. `/cmd_vel_mpc` 与 `/motion_control` 各有唯一 publisher；不能以“主题存在”替代 ownership 证据。
6. `ROGMap source_generation`、adapter `publication_sequence`、MINCO local snapshot generation、`goal_id`、`localization_epoch`、`plan_request_sequence` 和 `command_sequence` 是不同身份域，不能宣称编号端到端相等。

## 16. 坐标、时间、地图和 snapshot 契约

### 16.1 坐标与单位

| 对象 | 当前约定 |
| --- | --- |
| MPC state | world frame `[x, y, yaw]` |
| MPC control | body frame `[vx, vy, wz]`，单位 `m/s, m/s, rad/s` |
| ROGMap projection | world/map frame，由 service response 的 frame、origin、yaw 明确给出 |
| JPS grid | snapshot 的 map frame，栅格索引不是 ROS 坐标 |
| MINCO position | map/world frame连续位置，yaw 单独规划 |
| 底盘输入 | `/cmd_vel_mpc` 经 bridge 转成底盘约定的 `motion_control` frame |

离散 SE(2) 模型为：

```text
x_next   = x + dt * (vx*cos(yaw) - vy*sin(yaw))
y_next   = y + dt * (vx*sin(yaw) + vy*cos(yaw))
yaw_next = wrapToPi(yaw + dt*wz)
```

此模型只描述底盘中心运动学。轮心速度、舵角速率和轮速变化是后续真实四轮可行性检查，不会把舵角伪装成 MPC 的独立状态。

### 16.2 时间与新鲜度

控制循环默认 `20 Hz`，`dt=0.05 s`，horizon 为 `30`，预测时域约 `1.5 s`。观测时间、ROS time/sim time 和 steady clock 必须分开：

- projection service deadline 使用 steady clock，超时清除 client pending request，允许新请求重试；
- adapter status 是续租 heartbeat，不是永久 ready；lease 超时立即令规划输入失效；
- reference 的每个 pose 保留相对时间，Goal Manager 在最终提交点统一重定时；
- 旧 reference、旧 localization epoch、旧 goal 或迟到 service response 不能在急停恢复后重新驱动车辆；
- ROS topic 的跨 topic 发布没有 DDS 原子事务，必须靠同一互斥提交区和身份复核保证恢复顺序。

### 16.3 PlanningMapSnapshot

`ats_rog_map_adapter` 直接调用 `/rog_map/get_ground_projection` 数值 service，不能订阅 `/rog_map/esdf` 或 `/rog_map/viz` 的 `PointCloud2` 后反解析 signed distance。snapshot 至少包含：

```text
frame_id
origin_x, origin_y, origin_yaw
resolution, width, height
fused occupancy (-1 unknown, 0 free, 100 occupied)
signed distance
world-frame gradient
ROGMap source_generation
adapter publication_sequence
localization_epoch
projection/status timestamps
```

JPS、二维 RC-ESDF、MINCO clearance、footprint gate 和 Local Collision Repair 在一次规划中使用同一个 immutable local snapshot。当前消息链没有让每个下游都携带同一 source generation，因此只能证明“单次规划内 snapshot 一致”，不能宣称 ROG source generation、adapter sequence 和 MINCO generation 数值相等。

融合必须遵循以下真值表：

| 来源证据 | 输出语义 |
| --- | --- |
| 任一新鲜来源 occupied | occupied，不能被其他来源 free 覆盖 |
| 至少一个明确 free 且没有 occupied | free，可消解其他来源 unknown |
| 所有来源都无 free/occupied 证据 | unknown，按障碍处理 |
| outside-map 或 stale/lease 失效 | unknown/unready，触发 fail-closed |

静态图分辨率、origin 或 yaw 与 planning grid 不一致时，必须按输出 cell footprint 覆盖的所有源 cell 做保守聚合；不能只采样输出中心。ROGMap 的几何范围只是该来源的数据范围，范围外的 `-1` 不能覆盖另一来源明确的 free/occupied。ego unknown 清理默认关闭（`0.0`），只有完成带 yaw 的 `0.70 m x 0.55 m + margin` 定向矩形栅格化和边界测试后才可启用，绝不能用外接圆清除 footprint 外 unknown 或覆盖 occupied。

## 17. Goal Manager 和 ExecutionCommand

### 17.1 请求身份

Goal Manager 是执行授权 owner。一个 Path 或 `emergency_stop=false` Bool 都不是执行授权。每一次 goal/重规划请求都必须通过以下身份字段关联：

```text
goal_id
localization_epoch
plan_request_sequence
ROGMap source_generation
map_generation
map_publication_sequence
command_sequence
manager_incarnation
gimbal request/feedback sequence
```

定位重置、急停、goal cancel、preempt 或 manager 重启都会使相关旧身份失效。迟到 candidate/status 只能被记录和拒绝，不能恢复旧轨迹。

### 17.2 最终提交点

MINCO 产生的 candidate 进入最终 reference 前，Goal Manager 在同一提交互斥区依次复核：

1. active `goal_id`、localization epoch、plan request sequence 仍匹配；
2. candidate 的 frame、时间戳、finite 状态和 reference horizon 有效；
3. snapshot/status 的 `publication_sequence`、heartbeat 和 lease 仍新鲜；
4. 当前机器人和目标均 inside-map；起点、终点及定向 footprint cell 为 free；
5. `0.70 x 0.55 m + margin` 的 yaw-aware footprint 没有 unknown/occupied；
6. yaw authority policy、gimbal request/feedback sequence 仍匹配；
7. 重新计算统一 reference 时间基准；
8. 生成新的 `ExecutionCommand::MODE_EXECUTE` 和 `command_sequence`。

提交成功后才允许 MPC 接收新 reference。若任何一项失败，保持或发布 `MODE_STOP`，清空 tracker，输出零速度。不能通过放宽 MPC 的旧 reference 拒绝规则修复这类时序竞争。

### 17.3 进展和重规划

“一个离散点暂时不可过”不能让机器人永久停住。PlanProgressWatchdog 使用 steady clock 记录：

```yaml
progress_min_delta_m: 0.10
replan_stall_timeout_sec: 4.0
replan_min_interval_sec: 2.0
max_consecutive_replans: 2
```

看门狗同时检查当前位置、active plan、地图/TF/health、最后有效 reference 和 bounded replan 次数。健康暂态进入 map-wait/recovery；健康条件完整且有界重规划耗尽后，才返回 `RESULT_PLANNING_FAILED`。它不通过重复发送相同旧 Path 来“恢复”车辆。

## 18. JPS：离散全局拓扑路线层

### 18.1 作用

`GridJps` 在 immutable occupancy/signed-distance snapshot 上进行离散拓扑搜索，回答的是“哪些栅格相连、目标是否可达”。JPS 利用规则栅格上的跳点和邻居剪枝减少搜索节点；它输出的是栅格/世界坐标序列，不是时间化控制轨迹。

JPS 可以在实现允许的条件下受控 fallback 到 `GridAstar`，但 fallback 必须在同一 snapshot、同一 unknown/occupied 语义和同一 footprint gate 下执行。JPS/A* 都不能越过 occupied、unknown、outside-map 或 footprint 不可行 cell。

### 18.2 不由 JPS 负责的内容

JPS 不负责：

- 连续曲线平滑和 MINCO 优化；
- 时间分配、速度、加速度和 jerk；
- 独立 yaw 或云台补偿策略；
- 四轮舵角、轮速和 MPC 控制量；
- 轨迹发布、ExecutionCommand 授权或急停恢复。

因此 RViz 中淡蓝色的 `/minco/raw_path` 应标为 `Global Planning / JPS Search Path`。它表示离散全局搜索结果，不是 MPC predicted path，也不是底盘逐点跟踪 reference。全局规划、局部候选和 MPC 预测必须使用不同 topic、namespace、颜色和 legend，避免把搜索拓扑误判为执行轨迹。

### 18.3 JPS 的输入审计

规划前应记录：

```text
snapshot frame/origin/yaw/resolution
source and publication generation
start/goal grid index and world pose
unknown/occupied policy
oriented footprint margin
JPS expansion count
fallback reason (if A* used)
```

起点、终点或中间路径 cell 只要在当前 snapshot 中 outside、unknown 或 occupied，就必须拒绝 candidate 或触发 bounded replan；不能由 RViz 显示为空白推断为 free。

## 19. MINCO S3：连续、时间化的局部参考

### 19.1 数据流

MINCO 的职责是把 JPS 拓扑路径变成可执行前的连续候选：

```text
JPS raw path
  -> waypoint/path preparation
  -> MINCO S3 position optimization
  -> segment time allocation / time scaling
  -> independent yaw spline and authority policy
  -> signed-distance / clearance annotation
  -> oriented footprint safety
  -> Local Collision Repair
  -> candidate reference
  -> Goal Manager final commit and retiming
```

MINCO S3 不是简单线性插值。它通过分段多项式和时间分配控制位置连续性、速度/加速度边界以及平滑代价；轨迹是否最终可执行仍要经过地图快照和 footprint 检查。

### 19.2 独立 yaw

位置和 yaw 不应被强行绑定为单一航向规则。`YawSplinePlanner`/`YawAuthorityPolicy` 根据路径切向、目标姿态、gimbal compensated 或 body-yaw-follow 选择 authority，并生成独立 yaw spline。gimbal compensation 和 body-yaw-follow 是不同策略，不能混写为“MINCO 自动解决 yaw”。

每个 candidate pose 必须携带 position、yaw、relative time 以及必要的 clearance/authority 标记。yaw wrap 使用 `[-pi, pi]` 约定，跨越 ±pi 时应按最短连续方向处理，不能把数值跳变当作真实大角度旋转。

### 19.3 候选不等于执行 reference

`/minco/reference_path_candidate` 是规划器内部或诊断用的候选，不得直接驱动 MPC。candidate 必须通过：

- map snapshot generation/status 复核；
- 起点、目标和全轨迹 oriented footprint 检查；
- clearance 下界和局部 repair；
- goal、localization、request identity 复核；
- 统一重定时和 `ExecutionCommand` 提交。

只有最终 `/minco/reference_path` 才能被 `TrajectoryTracker` 接收。若提交失败，MPC 清空 tracker，保持零速度，不复用上一条 reference。

## 20. Footprint 安全与 Local Collision Repair

### 20.1 定向矩形

四舵轮车体 footprint 不是一个与 yaw 无关的点。安全检查至少使用 `0.70 m x 0.55 m + margin` 的定向矩形，将矩形四角、边界覆盖的栅格和 signed-distance margin 映射到 snapshot frame。必须测试：

- yaw 为 `0`、`pi/2`、跨越 `pi` 的情况；
- footprint 边界恰好落在 cell 边界；
- 非整除 resolution 和带 yaw 的 origin；
- unknown、occupied、outside-map 的 fail-closed 结果；
- occupied 不被 ego cleanup 覆盖。

外接圆只能作为更保守的拒绝近似，不能用来清除 footprint 外的 unknown，也不能把圆形通过写成矩形通过。

### 20.2 Local Collision Repair

Local Collision Repair 在 immutable snapshot 上对 MINCO candidate 的局部冲突段进行受限修复，例如调整局部 waypoint、时间或安全走廊。修复后的轨迹必须重新执行全轨迹 footprint safety、clearance 和时间边界检查；不能只检查被修改的一个点。

修复失败时必须区分：

```text
candidate unsafe -> bounded repair
repair exhausted -> bounded replan
replan exhausted with healthy inputs -> planning failed
transient map/TF/health failure -> recovery/map-wait
```

这套状态机解决“一个点过不去就卡住”的问题，但不会在地图不新鲜或状态未知时强行运动。

## 21. MPC 接收的是执行授权后的 reference

### 21.1 TrajectoryTracker

`TrajectoryTracker` 负责把最终 reference 按时间解析为 MPC horizon：

1. 校验 frame、时间戳和 finite 数值；
2. 根据当前 localization 将机器人状态投影到 reference；
3. 计算世界系位置/yaw 误差和相对时间；
4. 生成长度为 `horizon=30` 的 state/control reference；
5. 在 reference 不足、过期或 identity 不匹配时拒绝并请求 stop/recovery。

它不会重新做 JPS、MINCO 或地图融合。MPC 输出只取 `controls.front()` 作为当前控制周期命令，后续控制周期重新读取最新状态和授权 reference。

### 21.2 iLQR 默认求解

当前默认 `solver_mode=ilqr`。主要流程是：

```text
warm start
  -> nonlinear rollout with Se2Model
  -> cost and terminal cost
  -> linearization / Jacobian
  -> backward pass
  -> line search
  -> candidate control sequence
  -> body velocity and four-wheel safety validation
  -> controls.front()
```

warm start 使用上一序列和当前 reference control 的混合，当前代码中的比例为：

```text
u_warm = 0.7 * u_previous + 0.3 * u_reference
```

代价和迭代参数以受版本控制的 YAML 为准：

```yaml
state_weight: [18.0, 18.0, 4.0]
terminal_weight: [28.0, 28.0, 8.0]
control_weight: [0.12, 0.12, 0.08]
control_delta_weight: [0.7, 0.7, 0.25]
max_iterations: 6
regularization: 1.0e-5
line_search_decay: 0.5
min_line_search_step: 0.05
convergence_tolerance: 1.0e-3
```

这些权重只影响执行跟踪层，不能替代 MINCO 的平滑和地图 clearance 目标。

## 22. 四舵轮真实可行性约束

### 22.1 轮心速度

四个轮心相对车体中心的位置为：

```text
(+0.270, +0.270), (+0.270, -0.270),
(-0.270, +0.270), (-0.270, -0.270)   [m]
```

给定 body Twist `[vx, vy, wz]`，第 `i` 个轮心速度为：

```text
v_i = [vx - wz*y_i, vy + wz*x_i]
```

当前配置：

```yaml
wheel_base_x: 0.270
wheel_base_y: 0.270
max_wheel_speed: 1.6689711
max_wheel_acceleration: 2.0
max_steer_rate: 10.4719755
```

检查顺序必须保持：

1. 对 body velocity 做基础边界检查；
2. 根据四个轮心速度检查最大轮速；
3. 检查轮速度增量和等效轮加速度；
4. 检查有效轮速方向的舵角速率；
5. 若 wheel speed 超限，对完整 `[vx, vy, wz]` 做等比例缩放，再重新计算四轮量。

不能独立缩放某一只轮，否则四个轮的速度不再对应同一个刚体 Twist。轮速度向量增量是硬约束；有效方向之间的舵角变化也是硬约束。对方向向量点积取绝对值会把 180 度反向错误地当作 0 度变化，禁止这样实现舵角速率检查。

### 22.2 ZeroSpeedGuard

轮速接近零时，方向角没有定义，直接线性化舵角会产生伪约束和零速抖动。`ZeroSpeedGuard` 使用滞回：

```yaml
enter_threshold: 0.01
exit_threshold: 0.02
```

进入零速区域后只跳过“舵角方向”约束，并清除无效的方向记忆；它仍然检查：

- wheel velocity increment；
- body acceleration；
- maximum wheel speed；
- emergency stop；
- map/reference/health safety gate。

ZeroSpeedGuard 不是“零速时放行”，而是避免在方向未定义时制造错误舵角约束。

## 23. LTV-QP/OSQP shadow 的当前边界

导航仓已经有 backend-neutral QP 契约和 OSQP v1.0.0 适配，但它仍是 shadow 诊断路径：

```yaml
solver_mode: ilqr
qp_max_iterations: 400
qp_time_limit_ms: 10.0
qp_max_primal_residual: 1.0e-4
qp_max_dual_residual: 1.0e-4
qp_max_tracking_slack: 0.0
qp_max_hard_constraint_violation: 1.0e-7
```

每个 shadow 周期使用与 iLQR 相同的冻结 `ControlCycleSnapshot`，覆盖 current state、reference、求解前 last control、ExecutionCommand identity、localization epoch 和地图 generation。QP 过程为：

```text
same ControlCycleSnapshot
  -> fixed CSC LTV-QP
  -> OSQP v1.0.0
  -> delta_u reconstruction to absolute control
  -> shared Se2Model nonlinear rollout
  -> independent hard-check
```

必须同时满足 `solved`、finite、维度正确、iteration/deadline、primal/dual residual、slack/hard violation、输入健康、急停、localization、lease、gimbal、collision/map gate 才能标记 candidate feasible。以下状态全部拒绝：

```text
solved_inaccurate
max_iterations
timeout/deadline miss
primal or dual infeasible
numerical failure
non-finite result
ZeroSpeedGuard direction violation
独立四轮硬约束失败
地图/footprint producer 缺失
```

`qp_shadow` 不发布 `/cmd_vel_mpc`，不写 tracker、不改变 iLQR warm start、不改变 ExecutionCommand 或 emergency-stop。`solver_mode=qp` 当前仍显式拒绝启动。不得通过提高最大迭代次数、放宽 residual/deadline、接受 non-solved warm-start 或用 iLQR 运行冒充 QP shadow 证据。

## 24. ROS ownership、QoS 和故障恢复账本

### 24.1 唯一所有权

必须通过 ROS graph 和运行日志交叉确认：

```text
/rog_map_adapter/planning_map_snapshot   -> adapter 唯一 publisher
/minco/reference_path                     -> Goal Manager 提交后的唯一执行 reference
/cmd_vel_mpc                              -> ats_swerve_mpc 唯一 publisher
/motion_control                           -> twist_to_motion_ctrl 唯一 publisher
```

RViz display、debug candidate、`/minco/raw_path`、MPC predicted path 都不是速度 owner。不要把某个 topic 能被 `ros2 topic echo` 看到写成“控制链通过”。

### 24.2 QoS

PlanningMapSnapshot 使用可靠、可供 late joiner 获取的 QoS；执行 reference 当前 publisher 使用 `RELIABLE + VOLATILE`，观察脚本必须使用匹配 QoS，不能用错误的 `TRANSIENT_LOCAL` 观察结果推断旧 reference 是否复活。每次故障证据应记录 topic type、publisher/subscriber 数、reliability、durability、depth 和 frame。

### 24.3 fail-closed 状态表

| 失效 | 规划状态 | 安全输出 |
| --- | --- | --- |
| ROGMap projection timeout/stale | map-wait/recovery | emergency stop + 两级速度为零 |
| adapter lease/heartbeat 过期 | map-unready | emergency stop + 清空 tracker |
| all unknown / occupied / outside-map | planning failed 或 recovery | 不提交 candidate，速度为零 |
| TF/localization NaN 或 epoch 变化 | localization recovery | 丢弃旧 reference，速度为零 |
| candidate footprint unsafe | bounded repair/replan | 不发布 unsafe reference |
| iLQR/MPC 无解或约束失败 | control recovery | 确定性零速度 |
| bounded replan 耗尽且输入健康 | `RESULT_PLANNING_FAILED` | 保持急停 |

恢复必须确认 generation/heartbeat 继续递增、当前身份仍有效、没有新目标时迟到 response 和急停前 reference 不会恢复运动。`/planner/emergency_stop` 与 `/minco/reference_path` 是两个独立 DDS topic；安全性来自提交点身份和重定时契约，不来自 DDS 跨 topic 原子顺序。

## 26. 实车测试 Gate

实车测试必须分阶段，先保护底盘，再验证完整导航。满足以下条件前，不允许把代码当作无人值守实车闭环：

### Gate 0：构建和静态契约

- 三仓 `develop` 与远程一致，只有单一作者 `liukong1220`；
- 目标机 clean build、相关 GTest、launch syntax、QoS/frame/ownership 审计通过；
- `solver_mode=ilqr` 默认，`solver_mode=qp` 拒绝；
- 实车参数、轮距、轮速、舵速、急停输入和速度 frame 已由硬件负责人确认。

### Gate 1：底盘静态与低速

- 车轮离地或机械安全支架下验证零速、单轮方向和四轮刚体 Twist 一致性；
- 急停、通信丢失、定位 NaN、地图 lease 失效均在限定时间内输出 `/cmd_vel_mpc=0` 与 `/motion_control=0`；
- 先以 `vx`、`vy`、`wz` 单轴低速命令验证，不接近 max wheel speed/steer rate；
- 记录舵角方向过零、机械限位、轮速增量和停止延迟。

### Gate 2：受控地图和单目标

- 真实 Point-LIO、ROGMap projection、adapter snapshot、Goal Manager 和唯一速度链稳定运行；
- 机器人周围人工确认 free，目标短距离、低速、可人工接管；
- 记录 localization epoch、source/publication generation、command sequence、reference freshness 和控制周期 p50/p95/p99；
- 禁止同时启用未经验证的 QP 主控制链、红框障碍或高速度。

### Gate 3：故障和恢复

- 在空旷区域注入 input stale、projection timeout、adapter lease、unknown 和 unreachable，各使用独立运行；
- 逐项观察 `ready=false -> emergency_stop=true -> /cmd_vel_mpc=0 -> /motion_control=0`；
- 恢复后 generation 继续递增，旧 goal/reference 不复活；
- 有界重规划耗尽后返回明确 result，而不是无限重试或永久卡住。

### Gate 4：逐步扩大路线

- 先 nominal，再低复杂度局部障碍，再红框/狭窄区域；
- 每次只改变一个风险变量，保留 rosbag、节点图、参数快照和终点误差；
- 物理接触必须由独立 evaluator 或硬件安全记录确认，不能由 footprint 离散检查推导；
- 只有 Gate 0--3 全部有证据且 Gate 4 的受控路线稳定，才可进入有人值守的完整实车导航。

QP 主控制切换还需要额外的目标机实时性和 paired shadow 证据；当前不能因为 OSQP 已接入就直接进入实车 QP。

## 29. 最终边界

当前系统的准确称呼是：

> 基于 ROGMap 数值地面快照、Goal Manager 执行授权、JPS 离散拓扑搜索、MINCO S3 连续位置轨迹、独立 yaw、定向 footprint 安全与 Local Collision Repair 的四驱四转舵轮 SE(2) iLQR-MPC 规控链；OSQP LTV-QP 目前仅作为同周期 shadow 诊断。

这一定义同时解释了为什么不能只问“MPC 求解器是不是 QP”：QP 只替换执行层的一种局部优化内核，不能替换 JPS 的可达性、MINCO 的平滑时间化、footprint 的碰撞语义、Goal Manager 的授权身份或 fail-closed 故障恢复。P2/P3、HIL 和实车测试必须按本文件的分层 Gate 单独形成证据。
